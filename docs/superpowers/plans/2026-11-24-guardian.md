# G7 Guardian cabinet (session S7, slug `guardian`, migrations 0060-0064)

Scope = design section 4 / G7. Staged in ONE delivery (all three stages are in this PR, each usable on its own):
1. **Telegram bot buttons** (inline keyboards, answers only to what the guardian taps or writes),
2. **Telegram Mini App** (page `/ui/guardian`, login = Telegram `initData` check),
3. **standalone web portal** (the same page opened in a browser, login = phone + one-time code that arrives in the
   guardian's own Telegram chat).
API product: all three. Sheets edition: the OWNER side only (linking, one-time codes, approvals).

## What a guardian sees (read only, linked students only)
attendance (and what the make-up rights are), debt + payment plan, receipts/invoices (PDF), lesson schedule
(upcoming lessons incl. moves/cancellations), results (notes/grades, exams, approved progress reports, certificates;
G4 data, drafts are never shown).

## Linking (all four methods)
| Method | How | Result |
|---|---|---|
| one-time code | staff issues an 8-char code for a student (optionally for one guardian), valid 72 h, single use, stored hashed; guardian sends `/start CODE` (or the code) to the bot | link active at once |
| phone via Telegram contact | guardian shares his contact; accepted only when Telegram says it is his own number (`contact.user_id == from.id`) AND a guardian of the center has that number | link active |
| student QR card | guardian sends the code printed on the card (`NZQ1-...`) | **pending**: the center approves (a card can be photographed) |
| manual | staff links a Telegram id / guardian record by hand | active |
Before anything is shown the guardian must accept the privacy consent in the bot/page (`data_consents`
`data_processing` + `notifications`, given by the guardian). No consent = empty cabinet.

## Guardian actions (EVERY one needs the center's approval; nothing takes effect before)
| Action | Guardian gives | On approval |
|---|---|---|
| absence reason | upcoming lesson of his student + reason (before the lesson starts) | attendance `excused` for that lesson (existing make-up/credit rules run through `sync_entitlement`) |
| payment promise | date (<= `guardian_promise_max_days`, default 14) and optional amount <= debt | promise recorded (`payment_promises`), shown to staff; no money moves |
| make-up slot | an OPEN make-up right + one of the offered slots (other groups of the same course with free seats, within the right's validity) | make-up lesson scheduled for the right via the existing schedule path (conflict checks) |
Staff approves/rejects in the API (`/v1/guardian/requests/...`) or Sheets menu. The guardian sees the status in the
cabinet. **No push message is sent when staff decides** (Model B: pull only). The only things the bot ever sends are
answers to the guardian's own tap/message and his own login code (a reply to his own request).

## Security model
- Guardian session = opaque random token (stored as sha256), 12 h portal / 24 h Mini App, revocable; staff JWTs and
  guardian tokens are different dependencies and never interchange.
- DB fence (defence in depth): `Session.guardian_id` -> `app.guardian_id`; RESTRICTIVE policy `guardian_fence` on every
  table the cabinet reads, so even a buggy query returns only linked students' rows. Staff sessions are unaffected.
- Cross-center lookups before login go through SECURITY DEFINER functions (same pattern as the outbox worker).
- Branch scoping: new tables carry `branch_id` (strict, stamped from the student) and the `branch_scope` policy;
  catalog rows registered in `branch_catalog`.
- Bot webhook `/hooks/guardian-bot` checks `X-Telegram-Bot-Api-Secret-Token`; Mini App `initData` is HMAC-checked with
  the bot token, `auth_date` <= 24 h. Login codes: 6 digits, 10 min, 5 attempts, always answer 202 (no enumeration).
- All Telegram traffic goes through one transport object; tests use a fake that records calls (rule 8: no real messages).
